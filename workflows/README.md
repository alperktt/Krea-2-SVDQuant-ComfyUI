# Workflows

Four graphs. Drag the plain `.json` into the ComfyUI canvas — each opens with a **READ ME
FIRST** note carrying the settings that matter. The `*_api.json` twins are for POSTing to
`/prompt` from a script; they carry no layout, so don't drag those in.

| file | what it's for |
|---|---|
| `krea2_svdquant_diagnostics.json` | **Start here if anything is wrong.** No sampler, generates no image |
| `krea2_turbo_svdquant_w4a4_t2i.json` | Krea 2 **Turbo**, 8 steps, cfg 1.0 |
| `krea2_turbo_svdquant_w4a4_lora.json` | Turbo **with LoRAs**, chained through this repo's LoRA node |
| `krea2_base_svdquant_w4a4_t2i.json` | Krea 2 **base** (non-turbo), 50 steps, cfg 3.5 |

Everything under `workflows/` is generated by [`tools/build_workflows.py`](../tools/build_workflows.py).
Edit that script, not the JSON.

## What every graph needs

Three files, none of which are specific to this repo — any Krea 2 workflow uses the same two
and one checkpoint:

1. **A checkpoint** in `ComfyUI/models/diffusion_models/`, from
   [Hugging Face](https://huggingface.co/AlperKTS/Krea-2-SVDQuant-ComfyUI).
2. **Text encoder** `qwen3vl_4b_fp8_scaled.safetensors` in `ComfyUI/models/text_encoders/`,
   loaded with `CLIPLoader` type `krea2`.
3. **VAE** `qwen_image_vae.safetensors` in `ComfyUI/models/vae/`.

**Which loader node** depends on which checkpoint you downloaded, and getting this wrong is
the most common first-run failure:

| checkpoint | loader node |
|---|---|
| `Krea2-Turbo-W4A4-noLowRank` | the **stock UNETLoader** |
| any `SVDQuant-W4A4-rank*` | **Krea2 SVDQuant W4A4 Loader** (this repo) |

The `svdq` files carry extra `*.svdq_l1` / `*.svdq_l2` tensors that the stock loader does not
know about, which is why they need their own node.

A **red outline** on a loader means ComfyUI cannot find the filename in the dropdown — the
graph ships a suggested name, and yours may differ. Click the widget and pick your file.

## Diagnostics — run this before reporting anything

`krea2_svdquant_diagnostics.json`. Three steps, left to right, and the first one needs no
model at all so you can run it *before* downloading 8 GB.

**1. Env Check.** Answers the single most common report against this pack: *"the quantized
checkpoint is slower than fp8"*. Almost always the cause is that ComfyUI disabled
`comfy_kitchen`'s CUDA backend because torch was built against CUDA < 13 — and the fallback
dequantizes int4 in Python, so the checkpoint ends up slower than bf16, not faster. You want
to see:

```
cuda backend is live -- the int4 tensor-core kernel is available.
```

If you don't, install a **cu130 (CUDA 13) or newer** PyTorch build. Nothing else in this repo
will behave until that line is green.

**2. Load the checkpoint** you're diagnosing. Its `status` output names the kernel that will
actually run.

**3. Diagnostics**, `mode` widget:

| mode | what it tells you |
|---|---|
| `dispatch` | which kernel actually runs, per weight shape. **Start here** |
| `env` | versions and memory accounting, including where the low-rank factors currently live — under lowvram they should read `cpu` between steps, not `cuda` |
| `bench` | quantized vs bf16 timing per layer |
| `profile` | a `torch.profiler` table |
| `compile` | graph breaks a `TorchCompileModel` run would pay |

`tokens` is the sequence length to probe with — 4096 is 1024x1024. Kernel selection is
shape-dependent, so match your real resolution.

Neither node is cached: they re-measure the live process every run, which is the entire
point. **Paste both reports, your GPU, and the checkpoint filename into any bug report.**

## LoRAs

`krea2_turbo_svdquant_w4a4_lora.json`.

**Use Krea2 SVDQuant LoRA Loader, not the stock `LoraLoaderModelOnly`.** On a quantized
checkpoint the stock loader has to dequantize the 4-bit weight, add the LoRA, and requantize
it — which discards the format and quantizes the LoRA delta to 4 bits along with it. This
node attaches the LoRA as a parallel branch instead: `(W + BA)x == Wx + B(Ax)` is exact for a
linear layer, and the quantized weight is never touched.

**If a LoRA seems to do nothing, read the console.** The node prints what it matched:

```
224 quantized layers, 32 normal layers
```

`0 quantized layers` means the LoRA does not target this model, and nothing will change no
matter what strength you set. That line is the first thing to check.

**Stacking.** Chain one node per LoRA — the shipped graph has a second one muted, press
`ctrl-B` on it to enable. The whole stack is refolded on each node, so strengths stay exact
however many you chain, and the runtime cost stays one pair of GEMMs rather than one per LoRA.

**Download rank 256 if you use LoRAs.** Without a LoRA, branch ranks 64 / 128 / 256 are
statistically indistinguishable. With one, rank 256 wins clearly and rank 64 loses most of its
advantage over having no branch at all — measured over 16 prompts x 2 seeds x 4 adapters in
[BENCHMARKS.md](../BENCHMARKS.md#test-3--paired-lpips-fidelity-with-and-without-a-lora).

**The `adapters` input** only affects LoRAs that cannot fold into the branch — LoKr, LoHa,
OFT. A plain up/down LoRA ignores it.

| value | cost | what happens |
|---|---|---|
| `bypass` (default) | ~1.8 s per model call at 1440x1920 | exact; the 4-bit weight is never touched |
| `bake` | none per step | ComfyUI rewrites the weight once and the adapter delta is quantized to 4 bits with it |

## Turbo vs base

**Turbo** is cfg-distilled: `cfg` **must** be 1.0 and the negative prompt is zeroed
(`ConditioningZeroOut`) rather than encoded. Raising cfg degrades the image, it does not
sharpen it. 8 steps is what the checkpoint was distilled for.

**Base** is not distilled, so it uses real classifier-free guidance — cfg 3.5, a real negative
prompt through a second `CLIPTextEncode`, ~50 steps. There is no pre-built base checkpoint to
download; build one:

```bash
python quantize_krea2.py raw.safetensors --format svdq --rank 256 --variant base
```

That is roughly 12x the sampling work of the 8-step Turbo graph. Every benchmark number in
the README is Turbo at 8 steps — the ratios carry over, the absolute seconds do not.
